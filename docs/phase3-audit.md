# Phase 3 controlled Wayland benchmark

## Scope

This phase adds only a controlled native Wayland measurement client. It does
not load PulseSched, update scheduler maps, or use presentation feedback to
terminate an epoch.

## Implementation

Source: `benchmarks/wayland_interaction/benchmark.c`

The client:

- binds `wl_compositor`, `wl_shm`, `wl_seat`, `xdg_wm_base`, and
  `wp_presentation`;
- creates a minimal shared-memory XRGB surface;
- receives real pointer-button and keyboard-press events on that surface;
- assigns a monotonically increasing userspace `interaction_id`;
- records input and work timestamps with `CLOCK_MONOTONIC`;
- performs configurable busy CPU work;
- changes the frame color using the interaction ID;
- requests one `wp_presentation_feedback` object immediately before the
  corresponding surface commit;
- records presented timestamps and presentation flags; and
- records discarded, timeout, late-feedback, and protocol-error outcomes
  explicitly.

The output is JSON Lines on stdout. Each interaction and final trial record
contains the same interaction ID. Redirect stdout to a file under
`results/raw/` to preserve the raw measurement stream.

Arguments are:

```text
pulsesched-wayland-bench [work_ms] [trials] [feedback_timeout_ms]
```

The default is 20 ms CPU work, one trial, and a 1000 ms feedback timeout.
Trials are generated by real pointer-button presses or keyboard presses; an
input received while a previous feedback is pending is reported as
`input-ignored` rather than being silently merged.

## Build

The Makefile generates client bindings from the installed system protocols:

- `/usr/share/wayland-protocols/stable/presentation-time/presentation-time.xml`
- `/usr/share/wayland-protocols/stable/xdg-shell/xdg-shell.xml`

Build was verified with `wayland-scanner`, wayland-client 1.26.0, and the
system Wayland protocols package 1.49. Generated bindings and binaries are
ignored build artifacts; the protocol XML is not copied or modified.

## Runtime validation status

Build verified. The following still require a normal-scheduling interactive
run on the host:

- successful `wp_presentation` binding in this client;
- real input and independently numbered interactions;
- one matching feedback outcome per committed interaction;
- advertised presentation clock observation;
- multiple independently matched records; and
- an intentionally observed discarded or timeout case.

No causal attribution claim is made until those raw JSONL records exist.

## First host attempt

The client successfully bound `wp_presentation` and emitted:

```json
{"type":"capability","protocol":"wp_presentation","version":2,"clock_id":1,"clock_name":"CLOCK_MONOTONIC"}
```

The first run then aborted when GNOME/Mutter sent `xdg_toplevel.configure_bounds`
(opcode 2). The initial listener had NULL callbacks for the newer xdg-toplevel
events, producing libwayland's visible error `listener function for opcode 2 of
xdg_toplevel is NULL`. The listener now implements no-op callbacks for both
`configure_bounds` and `wm_capabilities`, and the client rebuild succeeds.
The aborted run is a protocol-integration failure, not causal benchmark
evidence.

## Validated host run

The corrected client was run under normal Linux scheduling with 20 ms CPU work
and three real interactions. The raw JSONL was saved under `results/raw/`.

Capability record:

```json
{"type":"capability","protocol":"wp_presentation","version":2,"clock_id":1,"clock_name":"CLOCK_MONOTONIC"}
```

All three interactions produced exactly one matching presented trial record:

| interaction | input to work | work to commit | commit to presentation | flags |
|---:|---:|---:|---:|---:|
| 1 | 100 ns | 20,097,315 ns | 21,075,984 ns | 7 |
| 2 | 51 ns | 20,094,957 ns | 21,128,892 ns | 7 |
| 3 | 40 ns | 20,087,168 ns | 23,876,419 ns | 7 |

This verifies userspace interaction IDs, one intended commit per interaction,
feedback association, monotonic presentation timestamps, and independent
matching across repeated trials. Flag value 7 reports vsync, hardware clock,
and hardware completion according to the protocol enum.

No timeout or discarded record has yet been collected. The client has explicit
non-success output paths for both; a short-timeout run is still required to
exercise that behavior rather than infer it from source inspection.
